结论先行。逆转裁判的乐趣核心并不依赖它的美术与声优演出，而在于一套可被文字完整承载的对抗结构：「证言 → 威慑 → 异议举证」的法庭循环与「调查 → 收证 → 心理枷锁」的探索循环交替推进。这两套循环天然适配纯前端文字对话式实现，可作为 NZCP 的骨架完整迁移；需要舍弃的是依赖触屏操作与实时演出的系统（科搜小游戏、情绪观察、逻辑象棋等）；值得延后到 v2 的是双线压力系统（裁判员/陪审团倾向）与多证人同时对峙。

一、逆转裁判机制调研

1.1 系列概况与核心玩法

《逆转裁判》（逆転裁判，Ace Attorney）是 CAPCOM 自 2001 年起推出的法庭文字冒险系列，玩家扮演辩护律师，通过调查取证与法庭辩论为委托人洗清罪名。系列正传历经 GBA 初代（2001）、NDS《复苏的逆转》（2005，新增章节与触屏调查）[3]、《逆转裁判2》（2002）[4]、《逆转裁判3》（2004）、NDS《逆转裁判4》（2007，王泥喜法介篇）[1]、3DS《逆转裁判5/6》、外传《逆转检察官》系列（检察官御剑视角，2009/2011）[9]，以及舞台移至 19 世纪末日英两国的《大逆转裁判》系列（2015/2017）[5]。

全系列由两套交替的核心玩法贯穿[2]：

  • 调查阶段（侦探部分）：在案发现场等场所自由移动、点击调查物品、与人物对话收集证物与线索；
  • 法庭阶段（庭审部分）：听取证人证词，通过「威慑」追问细节、以「异议！」出示证据指出证词矛盾，一步步逼近真相。

这套「调查 ⇄ 法庭」的交替结构形成明确的节奏曲线：开放式的探索收束为一条清晰的逻辑链，再在法庭的线性对抗中逐环释放。本项目的英文名缩写 NZCP（Ni Zhuǎn Cái Pàn）即对应中文「逆转裁判」。

1.2 核心对抗循环：证言—威慑—异议（系列的灵魂）

法庭阶段的心脏是围绕证言（证词）的对抗循环，其完整状态流程如下：

  1. 检察官传唤证人

    证人朗读证词，逐句显示，玩家可在法庭记录中随时查看所有证词原文。

  2. 威慑（ゆさぶる）

    对任一句证词按「威慑」逼问细节。威慑通常有三种结果：①证人补充细节（无代价的信息收益）；②证词被修正或追加——原作中大量关键破绽正是威慑逼出来的追加证词[3]；③威慑无意义（证词完美，检察官嘲讽压制）。

  3. 异议！出示证据（つきつける）

    针对某一具体证词，从法庭记录中选择一件证据或人物档案指出矛盾。指对则剧情推进（揭穿演出）；指错则遭到检察官反驳并由裁判长扣减生命值。

  4. 击破与连锁

    矛盾被击穿后，检察官不会认输：或诱导证人「修正记忆」给出新证词，或提出新指控。一段证言往往要经过 2～4 轮「证言→击破→新证言」的连环修正才能彻底逆转局面[3]。

  5. 终局

    裁判长宣判（无罪/有罪），或生命值耗尽、法庭无法继续时败诉（可从存档重试，无实质惩罚）。

这套循环的设计精妙之处在于：它把传统 AVG「满世界找选项」的探索压力，收敛为在一条 3～5 句的证词里反复挖掘的聚焦式解谜——玩家永远知道矛盾就藏在眼前的几句话里，但必须精确找出「哪一句」配「哪件证据」。

1.3 调查侧系统

  • 场景探索：移动（场景菜单）+ 点击调查（2D 背景/3D 模型上的热点），可能获得证据、触发对话或纯幽默互动（「梯子与人字梯」式经典冷场）。
  • 对话系统：话题列表制，新话题随剧情解锁；对 NPC出示证据可解锁隐藏话题——调查侧的「举证」与法庭侧共用同一套证据面板，是降低学习成本的关键设计。
  • 心理枷锁（勾玉系统，2代起）：调查中可「看见」NPC 心上的锁链。当对话陷入僵局时，用勾玉进入心灵枷锁模式，对 NPC 的隐瞒逐锁出示正确证据「啪」地断锁，全部解开才吐露真相[10][12]。该系统本质是「调查侧的小型证言循环」，把法庭对抗感带进了探索阶段。社区讨论普遍认为该设定虽然超现实，但框架严谨、从未被滥用[10]。
  • 逻辑系统（逆转检察官专属）：检察官视角下，将收集的碎片线索两两「连接」推导出新情报，以及与不肯开口者限时对峙的「逻辑象棋」[8]。

1.5 演出与叙事技法：为什么「逆转」体验成立

调研的核心目的不是罗列系统，而是提炼可迁移的设计原理。逆转裁判的体验由以下四条深层机制支撑，它们全部与「3D/声优/触屏」无关：

① 受控的信息释放阀门

证言机制把真相拆成「表面陈述（可看）→ 威慑细节（可挖）→ 矛盾点（必须击破）」三级。玩家在信息不完全时的每一次威慑都是主动的、必有回应的探索——这是开放感与确定感的精确平衡。

② 公平可解的解谜承诺

每个矛盾必有且仅有有限个正确答案，全部陈列于法庭记录中。失败代价低（扣一格血、可无限重试），保证了「挑战但不惩罚」的心流——这是文字推理游戏与硬核解谜的分界线。

③ 压力—释放的节拍同构

检察官的步步紧逼制造压力，「异议！」瞬间释放压力并立刻抛出更大的真相作为新压力。叙事节拍与玩法节拍完全同构，玩家不是「看剧情」，而是亲手敲响每一拍。

④ 角色即难度调节器

裁判长的摇摆＝节奏缓冲；助手的吐槽＝隐形提示系统；检察官的锋利＝紧迫感来源。角色不是剧情挂件，而是被写进玩法循环的「函数」。

二、机制迁移决策

对照第一章的机制清单，逐项给出 NZCP 的处理决策。判定标准有三：①文字交互能否无损承载（无损则迁移）；②无演出依赖时是否有替代形态（有则改造）；③实现成本与玩法收益之比（低收益高成本则舍弃或延后）。

三、NZCP 游戏机制设计

3.1 设计定位与技术约束

  • 定位：逆转裁判式文字对话推理游戏，纯前端单页应用，零后端、零构建、可离线、可双击即玩。
  • 案件即数据：一个 JSON 文件 = 一个完整案件（含人物、证据、调查、证言、结局）。引擎与内容彻底分离。
  • 剧本来源：①项目内置 cases/ 目录；②玩家从本地导入 .json 剧本（拖拽/文件选择）；③后续可扩展为粘贴文本导入。导入即校验，校验通过进入「我的案件」列表。
  • 素材降级：立绘、背景、BGM、音效全部可选。素材缺失时以「姓名牌 + 表情标签 + 纯文字」模式优雅运行——案件可读性永远优先于演出。
  • 写作协作：格式面向 AI 生成优化（见 4.1），目标是「同一格式 → 批量产出案件」。

3.2 游戏循环与状态机

引擎顶层状态机与剧本的层级严格同构：案件（case）→ 幕（act）→ 场景（scene）→ 指令（op）。

案件状态机
TITLE（主菜单：选案/导入）
  → PROLOGUE（开场脚本）
  → ACT loop ─┬─ investigation（调查幕）：场景间自由移动
  │             │    SCENE_ROAM ⇄ TOPIC_PLAY / EXAMINE_PLAY
  │             │    （每次交互后检测 goal.require_all → 全满足 → 播 on_complete → 下一幕）
  │             └─ trial（法庭幕）：线性执行 script
  │                  SCRIPT_RUN → TESTIMONY_LOOP ─┐
  │                     ▲    │ 威慑：播 press 脚本，可修正/追加证词
  │                     │    │ 异议：命中 contradiction → 播击破脚本，退出循环
  │                     │    │ 出错：扣 HP + 检察官嘲讽，留在循环
  │                     └────┘
  → VERDICT（判决演出）→ END / GAMEOVER（HP≤0 → 回最近检查点）

两幕型之间由 goal（调查幕推进条件）衔接：引擎持续检测条件令牌（证据已获得 / 话题已聊过 / 调查点已查过 / flag 已置位），全部满足才推进——这保证了自由探索的收敛性：玩家可以按任意顺序调查，但永远集齐关键线索后才开庭，不会出现「漏证据上法庭」的卡死局面。

四、剧本格式规范（NZCP Script Format 1.0）

格式规范正式定义于 script-format/script.schema.json（JSON Schema draft-07），本文说明其设计逻辑。一句话概括：一个 JSON 文件 = 一个案件；案件 = 元数据 + 人物 + 证据 + 若干幕；幕 = 场景 + 指令序列；交互以结构化指令封装，不要求作者写控制流。

4.1 设计原则（面向 AI 批量生成）

  1. 高频交互封装，低频分支通用。证言/举证/心理枷锁/选项被定义为自包含数据结构，循环、判定、惩罚、状态标记全部由引擎内置逻辑接管；剧本作者只填「内容」（台词、证据 ID、反应脚本）。这消除了生成剧本时最容易出错的环节——手写状态机。
  2. 状态隐式管理。话题聊过与否、调查点查过与否、证据在不在记录中、flag 值——全部由引擎按 ID 自动记账，剧本用声明式 token（如 "ev:ev_autopsy"、"tp:sc-detention:tp_secret"）引用状态，绝不手工维护。
  3. 语义 ID 前缀。char_/ev_/pr_ 人物证据、sc-/tp_/ex_ 场景话题调查点、st- 证词。校验器与人类都能一眼识别引用类型。
  4. 台词与结构分离。所有演出文本集中在 text 字段，结构字段不含叙述内容——便于校对、便于替换、便于将来本地化。
  5. 校验闭环。生成 → validator.js 校验 → 按错误路径修复 → 再校验。schema + 引用检查 + 结构可达性检查构成三层防线（4.5 节）。

4.2 顶层结构

{
  "format_version": "1.0",
  "case":       { 案件元数据 + prologue/epilogue 脚本 },
  "characters": [ { id, name, role, desc, sprites(可选) } ],
  "evidence":   [ { id, type: "evidence"|"profile", name, desc, hidden } ],
  "acts":       [ 幕：investigation（调查）| trial（法庭） ]
}

证据表里同时定义「物证」与「人物档案」（type=profile）——对应原作的法庭记录双页签；hidden: true 的条目开局不可见，须通过 evidence_add 获得并弹出「获得证据」演出。

4.4 核心数据模型：证言（testimony）

证言是格式的重心。一段证言的数据模型如下（摘自 schema，字段见 script.schema.json /definitions/Statement）：

{
  "op": "testimony",
  "title": "～案发当晚的目击～",
  "witness": "char_dojima",
  "hint": "证词的具体时间点……有能和它对质的资料吗？",   // 一级提示
  "penalty": { "amount": 1, "taunt": [ ...检察官嘲讽脚本... ] },
  "statements": [
    {
      "id": "st-1",
      "text": "晚上9点整，我亲眼看到被告从仓库里跑了出来！",
      "press": {                                          // 威慑（可选）
        "script": [ ...逼问对话... ],
        "new_text": "...",                                // 威慑后修正本句
        "insert_after": { "id": "st-1b", "text": "..." }  // 或追加新证词
      },
      "contradictions": [                                 // 可击破矛盾（可选）
        { "evidence": "ev_autopsy",
          "hint": "『9点』——敢和哪份记录对质？",          // 二级提示
          "script": [ ...异议！揭穿演出... ] }
      ]
    }
  ],
  "on_all_pressed": [ ...全部威慑完的彩蛋脚本... ]
}

引擎行为：进入证言后循环等待玩家「威慑当前句 / 切换证词 / 异议举证」。威慑播放 press.script 并可改写证词列表；举证命中 contradictions 中的证据则播放击破脚本并退出循环；举证未命中则按 penalty 扣血、播 taunt、留在循环。一个必胜点即可推进主线，多余 contradictions 与威慑信息构成玩家自由度——这正是原作「弹性结构、固定终点」节拍的格式化表达。示例剧本 example-case.json 的第 1～2 幕演示了完整两段连环证言（9 点时间矛盾 → 修正证言 → 黄雨衣矛盾），并附带 present 终极举证与 psyche_lock 心理枷锁，可直接作为案件创作的 few-shot 范本。

4.5 调查幕数据模型与校验规则

调查幕由场景（地点）组成：每个场景声明 topics（话题）、examines（调查点）、exits（出口）；幕级 goal.require_all 声明推进条件，全部满足后播放 on_complete 进入下一幕。话题与调查点的 requires 支持 token：证据已获得 / 话题已聊过 / 调查点已查过 / flag 已置位。

校验器三层检查（加载剧本时执行，错误带 JSON 路径）：

  • 语法层：JSON.parse；结构层：对照 schema（必填字段、枚举、ID 正则、数组约束）；
  • 引用层：所有 who / evidence / witness / exits.to / goto.label / requires / goal token 必须解析到已定义对象（本次示例剧本检查结果：0 错误）；
  • 可达层：每段证言至少含 1 个 contradiction 或其所在场景存在其他出路；goal.require_all 中的每个证据必然有 evidence_add 产出；goto 标签存在且不跨数组。

五、实施路线图

  1. v0.1 引擎原型

    打通 courtroom 侧最小闭环：say/narrate/fx + testimony + present + hp + verdict，跑通示例剧本的法庭幕。验收：示例案件法庭幕可玩、扣血与重试正确。

  2. v0.5 完整引擎

    补齐调查幕（场景移动/话题/调查点/goal 检测）、psyche_lock、checkpoint 存档、validator 校验器、本地导入剧本。

  3. v1.0 发布版

    主菜单与案件库、三级提示系统、移动端适配、设置（文字速度/音量）、通关评价（用时/扣血/提示次数）。

  4. v1.x 内容生产线

    以本格式 + 示例剧本为 few-shot 基准建立 AI 写案流程：生成 → 校验 → 修复循环；沉淀《剧本创作指南》。

  5. v2.0 机制扩展

    裁判员倾向条与最终辩论（4代/大逆转）、多证人同时作证（speaker 字段已预留）、证据细查子选项（科搜的文字化替代）。
